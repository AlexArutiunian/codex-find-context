# AGENTS.md

Этот файл задаёт правила работы coding-агентов в данном репозитории.
Он дополняет `README.md`: README описывает решение для человека, а здесь находятся рабочие инструкции для агента.

## 1. Приоритет источников

Перед изменениями сначала прочитай:

1. точное условие задания / список артефактов, если они уже добавлены в репозиторий;
2. `README.md` — текущее описание задачи и решения;
3. `docs/architecture.md` — архитектурные решения и ограничения;
4. существующий код и тесты;
5. этот файл.

Не придумывай требования, которых нет в условии или документации. Если приходится сделать допущение, сформулируй его явно и отрази в README/architecture, если оно влияет на решение.

Если точное условие только что получено, **сначала выпиши обязательные deliverables и критерии**, затем проектируй решение. Не начинай кодировать по памяти о похожих кейсах.

## 2. Главный режим работы: сразу чистый end-to-end

**Не делай baseline у baseline, MVP у MVP и бесконечную лестницу одноразовых прототипов.**

Baseline нужен только если он быстро снимает конкретную техническую неопределённость или даёт измеримую точку сравнения. Как только feasibility понятна, переходи к **первой чистой полезной end-to-end версии**, которую не стыдно показать проверяющему.

Предпочтение:

```text
маленький, но законченный продуктовый срез
>
несколько промежуточных полу-решений
```

Первая полезная версия должна по возможности сразу иметь:

- понятный пользовательский вход;
- основной happy path;
- ambiguity / failure / human-escalation path;
- traceability/evidence, если это AI case;
- один нормальный UI или API contract;
- ключевые тесты;
- README и архитектуру, соответствующие фактическому коду.

Не усложняй систему ради архитектурных слов. Но и не останавливайся на debug CLI, если за разумное время можно сделать demo-ready flow.

## 3. Общий порядок работы

Работай в следующем порядке:

1. Понять точное условие, входы, выходы, критерии и обязательные артефакты.
2. Быстро изучить существующую структуру репозитория и переиспользовать то, что уже есть.
3. Сформулировать короткий план с приоритетами и бюджетом времени.
4. Если есть серьёзная неопределённость — сделать только необходимый smoke-test/baseline для её снятия.
5. Собрать clean end-to-end happy path.
6. Добавить human escalation / controlled failure path.
7. Добавить тесты и минимальную evaluation-проверку.
8. Если требуется продуктовая часть — сделать её до финальной полировки, а не оставлять на последние минуты.
9. Синхронизировать README, архитектуру и команды запуска с фактическим кодом.
10. Оставить время на финальный run, проверку артефактов, секретов и git status.

Не расширяй scope без необходимости. Не делай большие рефакторинги «заодно».

## 4. Критерий выбора решения

Приоритет:

**корректность → понятность → воспроизводимость → demo-readiness → достаточная производительность → дополнительные улучшения.**

Предпочитай решение, которое можно объяснить, запустить и проверить, а не максимально сложную архитектуру.

Если есть несколько вариантов, коротко фиксируй trade-off и причину выбора текущего.

## 5. Интерфейсы, язык и готовые заготовки

### Язык UI

Если язык интерфейса **не задан условием**, для локального web/demo UI по умолчанию используй **русский язык**. Русскоязычному пользователю и проверяющему так быстрее ориентироваться в интерфейсе и результатах.

При этом **не переводи насильно устойчивые технические термины**, если английский вариант короче и понятнее. Нормально оставлять как есть:

- `RAG`, `LLM`, `embedding`, `reranker`;
- `Recall@k`, `Precision`, `ROC-AUC`, `PR-AUC`;
- `RICE`, `ICE`, `North Star`;
- `FastAPI`, `Gradio`, `Mermaid`, `Docker`;
- `happy path`, `fallback`, `human-in-the-loop`, если перевод делает текст тяжелее.

Не делай двуязычный интерфейс без необходимости. Лучше один ясный русский UI с уместными technical terms.

### Переиспользование вместо ручной верстки

Неключевые для кейса части **переиспользуй/шаблонизируй, а не пиши с нуля**.

Default toolkit:

- **Gradio** — быстрый web/demo UI для text/RAG, CV, agent, analytics и product demos;
- **Mermaid in Markdown** — архитектура, flow и sequence diagrams без отдельного build-step;
- **FastAPI** — только если нужен настоящий API/service contract;
- простые Markdown-таблицы — backlog, metrics, RICE/ICE, experiments;
- короткий ADR-style блок — для важного trade-off, если он нужен.

Не трать экзаменационное время на React/CSS/JS boilerplate, если frontend не является core deliverable. Если Gradio решает задачу — используй Gradio.

Если нужен красивый demo UI, он должен выглядеть как интерфейс продукта, а не debug-console.

### UI quality checklist

Перед тем как считать UI готовым, быстро проверь:

- понятны ли названия вкладок и полей без чтения кода;
- не рвутся ли слова по буквам;
- не съезжают ли таблицы;
- длинные таблицы лучше горизонтально скроллить, чем ломать заголовки;
- графики используют разумный data-driven scale, а не фиксированный диапазон, который сжимает все точки в угол;
- подписи не перекрывают друг друга; при необходимости показывай детали по hover;
- debug scores/trace не занимают основной пользовательский экран;
- критическое состояние (`ALLOW`, `DENY`, `MANUAL_REVIEW`, `ESCALATE_TO_HUMAN`, error) визуально считывается быстро.

## 6. Код

- Пиши простой, читаемый Python.
- Избегай clever one-liners, скрытой магии и ненужного метапрограммирования.
- Имена функций и переменных должны отражать смысл.
- Одна функция — одна понятная ответственность.
- Не создавай абстракции раньше, чем они реально понадобились.
- Не дублируй уже существующую функциональность без причины.
- Комментарии должны объяснять **почему**, а не пересказывать очевидный код.
- Ошибки не должны молча проглатываться.
- Не меняй публичный интерфейс без необходимости.
- Не добавляй новую зависимость, если задача просто решается уже имеющимися средствами.

Если код зависит от случайности — зафиксируй seed там, где это важно для воспроизводимости.

## 7. Структура репозитория и экзаменационные артефакты

Ориентируйся на текущую структуру:

```text
.
├── README.md
├── AGENTS.md
├── requirements.txt
├── setup.sh
├── .env.example
├── docs/
│   └── architecture.md
├── src/
└── tests/
```

Если условие требует дополнительные артефакты, добавляй их явно, например:

```text
product/
├── backlog.md
└── experiments.md

eval/
└── cases.json
```

Новые файлы добавляй только когда они упрощают структуру решения.

Не складывай всё в один огромный файл, но и не дроби небольшой PoC на десятки модулей.

### Типовой checklist для 4-hour System Design case

Если это совпадает с условием, постарайся закрыть:

- `README.md`: problem/value, что реализовано, setup/run/demo, limitations;
- `docs/architecture.md`: Mermaid diagram, data flow, trade-offs, failures, scale/privacy;
- `src/`: runnable PoC;
- `tests/`: happy path + human escalation/failure path;
- sample/synthetic input, если реальные данные нельзя коммитить;
- evaluation/example cases;
- product page: hypotheses + RICE/ICE + effect + experiment, если требуется продуктовым треком.

Всегда сверяй этот список с **точным условием**, а не считай его автоматически обязательным.

## 8. System Design

Для системного решения явно проверь следующие вопросы.

### Functional requirements

- кто пользователь системы;
- какой вход приходит;
- какой результат должен вернуться;
- какие основные сценарии обязательны;
- что находится вне scope.

### Non-functional requirements

Если они релевантны задаче, оцени:

- latency;
- throughput / нагрузку;
- доступность;
- масштабирование;
- стоимость;
- требования к данным и приватности.

Не выдумывай точные числа, если их нет в условии. В таком случае помечай их как допущения.

### Data flow

Архитектура должна позволять однозначно проследить путь данных:

`input → validation/preprocessing → core logic/model → storage/integrations → output`.

Для каждого важного компонента должно быть понятно:

- что он делает;
- почему он нужен;
- почему выбран этот подход;
- что произойдёт при его отказе.

### Обязательный happy path и escalation

Если система принимает автоматическое решение, архитектура и PoC должны явно показывать как минимум два пути:

```text
normal / confident input
    -> automated result

ambiguous / unsafe / low-confidence / failure
    -> clarification / MANUAL_REVIEW / ESCALATE_TO_HUMAN
```

Human escalation не должен быть только строкой в README: если время позволяет, покажи его в рабочем PoC/UI.

### Надёжность

Где применимо, продумай:

- sync vs async обработку;
- очереди и backpressure;
- retries;
- idempotency;
- timeouts;
- caching;
- graceful degradation;
- fallback;
- dead-letter / повторную обработку;
- human-in-the-loop.

Не добавляй Kafka, Redis, Kubernetes и другие компоненты просто «для солидности»: каждый компонент должен решать конкретную проблему.

## 9. ML / LLM / AI-компоненты

Если решение содержит ML/LLM:

1. Baseline используй только если он быстро проверяет конкретную гипотезу или нужен для сравнения; **не превращай baseline в конечный продукт, если уже очевидно, что нужен более сильный путь**.
2. Объясни, почему нужен ML/LLM, а не правила или более простой алгоритм.
3. Опиши вход модели и выход модели.
4. Не используй признаки или данные, недоступные в момент inference.
5. Определи offline-метрики качества.
6. Если это пользовательская система — укажи продуктовую/online-метрику.
7. Для confidence-based решений задай threshold/policy и поведение при низкой уверенности.
8. Продумай drift и мониторинг качества.
9. Для внешней модели/API предусмотри timeout, ошибки, лимиты и fallback.
10. Для LLM учитывай prompt injection и недоверенный внешний текст, если это релевантно.
11. Если есть retrieved evidence/sources — material claims должны быть traceable; fluent answer без evidence не считать успехом.
12. Не превращай `planned/proposed` в `completed fact`; временные и конфликтующие решения должны различаться.

Не представляй эвристику или экспериментальный PoC как production-ready решение.

## 10. Product track

Если в задании есть продуктовая часть, **не оставляй её на последние 10 минут**.

Подготовь законченный блок:

- пользователь / stakeholder / JTBD;
- проблема и текущий workflow;
- North Star + guardrails;
- минимум 5 осмысленных hypotheses, если формат задания это допускает;
- RICE/ICE или другой понятный приоритет;
- effect formula;
- experiment design;
- success threshold;
- stop / rollback criterion;
- staged rollout.

Для RICE явно показывай формулу:

```text
RICE = Reach × Impact × Confidence / Effort
```

Для эффекта можно использовать шаблон:

```text
expected_value = affected_events
               × baseline_cost_per_event
               × expected_relative_improvement
```

Каждое число помечай как **measured / estimated / assumption**. Не выдавай придуманный ROI за измеренный бизнес-эффект.

## 11. Данные и безопасность

- Никогда не коммить секреты, токены, пароли и реальные `.env`.
- Конфигурацию передавай через переменные окружения или безопасный config.
- Не логируй чувствительные данные без необходимости.
- Минимизируй сохраняемые персональные данные.
- Проверяй входные данные на ожидаемый формат.
- Не выполняй содержимое пользовательского ввода как код/команды.
- Не используй destructive-команды без явной необходимости.
- Если используются реальные приватные данные, не копируй их в public README/tests/screenshots/sample_data.

## 12. Ресурсы и производительность локальной машины

Скорость важна, но нельзя получать её ценой зависания системы, OOM, падения kernel/IDE или потери результатов.

Перед тяжёлым запуском оцени объём данных и ожидаемое потребление RAM/VRAM/диска. Во время длительных вычислений периодически контролируй ресурсы, например:

```bash
free -h
nvidia-smi
df -h
```

При необходимости используй `htop`/`top` и `watch -n 1 nvidia-smi`.

Правила:

- Не загружай весь большой датасет в RAM, если достаточно streaming/chunking, mmap, батчей или SQL/columnar-обработки.
- Не создавай несколько полных копий большого DataFrame/тензора без необходимости.
- Не запускай одновременно несколько тяжёлых процессов, которые конкурируют за один и тот же RAM, диск или GPU, если это не даёт измеримого выигрыша.
- Оставляй запас RAM для ОС, браузера, IDE и filesystem cache; не доводи машину до активного swap/thrashing.
- Если начинает быстро расти swap, интерфейс тормозит, kernel перестаёт отвечать или система близка к OOM — уменьши batch/chunk size, число workers/threads или останови дублирующий процесс.
- Для GPU подбирай batch size так, чтобы VRAM использовалась эффективно, но оставался разумный запас и не возникало CUDA OOM.
- Если GPU нужен вычислению, проверяй, что код действительно использует GPU, а не случайно работает на CPU.
- Не стремись к 100% RAM/VRAM любой ценой. Цель — максимальная **устойчивая** производительность без риска потерять процесс и время.
- Для CPU не выставляй число workers/threads вслепую.
- Для I/O-heavy задач не увеличивай параллелизм, если диск уже является bottleneck.
- Долгие этапы по возможности должны сохранять промежуточный результат/checkpoint.
- Перед повторным тяжёлым запуском проверь, не остался ли предыдущий процесс в фоне.
- После экспериментов освобождай ненужные модели и фоновые процессы, если они мешают следующему этапу.

Оптимизируй только после измерения.

Если есть выбор между немного более быстрым вариантом с высоким риском OOM и немного более медленным устойчивым вариантом — для ограниченного по времени задания выбирай устойчивый вариант.

## 13. ETA, бюджет времени и контроль долгих процессов

В этой задаче время ограничено. Нельзя запускать потенциально долгий процесс и просто ждать его завершения без оценки длительности и проверки прогресса.

### Обязательное правило ETA

Перед каждым потенциально долгим действием — обучение, inference по большому объёму, индексация, embeddings, скачивание большой модели, preprocessing, benchmark, конвертация модели, массовый API-вызов или другой этап дольше примерно одной минуты — **сначала оцени ETA**.

Перед запуском сообщи пользователю кратко:

```text
Что запускается: ...
ETA: ~... минут
Основание оценки: ...
Критерий остановки/проверки: ...
```

Если точную оценку заранее получить нельзя, сначала сделай небольшой timed smoke-test/sample и экстраполируй время полного запуска.

### Во время выполнения

- Показывай progress bar, throughput или `done/total`, если процесс существенный.
- Если процесс идёт заметно медленнее первоначальной оценки, пересчитай ETA.
- Если ETA перестаёт оставлять запас на интеграцию, тесты, README и сдачу — остановись и выбери более дешёвый путь.
- Если throughput близок к нулю или процесс явно завис — не жди вслепую.

### Не тратить время на пустые гипотезы

Перед экспериментом сформулируй:

1. какую гипотезу он проверяет;
2. какую метрику/результат ожидаем увидеть;
3. сколько времени максимум готовы на него потратить;
4. при каком результате эксперимент прекращаем.

Smoke-test нужен для снятия неопределённости, **а не как повод плодить ещё один MVP**.

### Общий бюджет задачи

Всегда оставляй отдельный запас времени на:

- интеграцию;
- smoke-test / pytest;
- исправление последней ошибки;
- README и `docs/architecture.md`;
- product artifacts, если они обязательны;
- `git status`, проверку секретов и финальный commit/push.

Не допускай ситуации, когда основной эксперимент заканчивается ровно к дедлайну.

## 14. Тестирование и проверка

После изменения запускай проверки, соответствующие масштабу изменения.

Базовая подготовка окружения:

```bash
./setup.sh
source .venv/bin/activate
```

Если есть тесты:

```bash
pytest -q
```

Для небольшого PoC допустим минимальный smoke-test, но он должен проверять основной happy path и хотя бы один важный ошибочный/escalation сценарий.

Перед завершением задачи проверь:

- код импортируется/запускается;
- happy path реально работает;
- escalation/fallback path реально работает;
- README-команды соответствуют реальности;
- тесты проходят;
- нет случайных абсолютных локальных путей;
- нет секретов;
- нет traceback/debug-мусора;
- нет критичных `TODO`;
- поведение соответствует заявленной архитектуре.

Если какая-то проверка не запускалась, не утверждай, что она прошла.

## 15. Документация

README должен позволять проверяющему за несколько минут понять:

- задачу и value;
- что реально реализовано;
- архитектуру;
- как запустить;
- как увидеть happy path;
- как увидеть human escalation/failure path;
- какие есть ограничения и trade-offs.

`docs/architecture.md` должен описывать фактическое решение, а не абстрактно возможную production-систему.

Для архитектуры по умолчанию используй Mermaid, если условие не требует другого формата.

Не дублируй одинаковый большой текст между README и architecture: README — краткое резюме, architecture — детали.

## 16. Работа с неоднозначностями

Если неоднозначность небольшая и не влияет на основной контракт — выбери минимальное разумное допущение и явно его запиши.

Если неоднозначность может радикально изменить API, архитектуру, данные или критерий успешности — не угадывай молча: обозначь проблему и запроси уточнение.

Если можно быстро проверить неопределённость чтением файла, кода, данных или коротким smoke-test — сначала проверь, а не задавай пользователю вопрос, который можно решить самостоятельно.

## 17. Definition of Done

Работа закончена не когда «есть код», а когда:

1. exact deliverables из условия отмечены как выполненные;
2. один clean end-to-end happy path реально запускается;
3. один human escalation / controlled failure path реально запускается;
4. architecture diagram соответствует реализации;
5. product artifacts заполнены, если требуются;
6. demo UI/API не выглядит как debug console;
7. UI быстро читается: язык понятен, таблицы не ломаются, графики имеют разумный масштаб;
8. tests/smoke checks green;
9. private data/secrets не staged;
10. README даёт fresh-run команды;
11. осталось время на финальную проверку и сдачу.

Финальный результат должен быть таким, чтобы проверяющий открыл репозиторий, быстро понял решение, запустил его и увидел и happy path, и безопасный failure/escalation path без догадок.
